A

Executive overview

FridgeFit tracks what a user actually has in their kitchen and tells them what they can cook with it. A user signs in, builds a pantry — by hand or by photographing a grocery receipt — and the app evaluates every recipe against that pantry to answer one question: can I make this? Three features use generative AI to cut the manual work: on-device receipt reading, on-device recipe ideas from the pantry, and remote ingredient substitutions.

✓What the audit found

The codebase is small, coherent and unusually disciplined: 7,760 lines of production Swift across 89 files, organised into a genuine SwiftUI / MVVM / Use Case / Repository separation where the layering is real rather than nominal. Views collect input, view models map state, and every rule lives in a use case behind a protocol with a test double.

The strongest property is architectural: no generative model is permitted to assert pantry state. Model output enters as an untrusted Raw* value and must pass a deterministic validator before any view sees it. Receipt items whose echoed source line was never sent are discarded outright — the hard stop on invented groceries. Each of the three AI features has a test asserting that adversarial case by name.

The gap is not code quality — it is evidence. All 240 tests pass, and all 240 run against doubles. No test and no runtime observation touches any of the four production integrations: Firebase Auth, Cloud Firestore, Apple Foundation Models, or OpenRouter. Two features are hardware-gated and cannot run on a simulator at all. One feature — ingredient substitution — is non-functional in this checkout because the gitignored Secrets.xcconfig is absent. That is why 14 requirements read Needs verification and 1 Blocked: the implementation reads correct, and correctness was not established.

Receipt Scanning · 6

▶CD-SCAN-03Deterministic receipt line parsingOCR output is reduced to candidate product lines by removing receipt furniture — totals, payment lines, store metadata — and splitting the trailing price off each description, without modifying the original text.✓CompletedP0

Implementation evidenceReceiptLineParser is a deliberately weak filter: it removes only what is unambiguously not a product, documenting that a wrongly dropped line is invisible to the user whereas a wrongly kept one costs one extra row the model will triage anyway. Metadata is matched as whole words so CASHEWS survives CASH and CARDAMOM survives CARD; multi-word phrases are matched as consecutive words; ambiguous leading words such as TOTAL are treated as metadata only when nothing alphabetic follows, so 'TOTAL 45.67' is dropped and 'TOTAL GREEK YOGURT 6.00' is kept. Price splitting works on the last whitespace-separated token and requires exactly two decimal places, which keeps 500G and 2L from being read as prices; a trailing tax flag token is tolerated. A leading 5+ digit barcode is stripped. A bare '2 @ $3.00' multiplier line is folded into the previous line rather than discarded. originalText is never modified.

◆Before this project can be declared complete

Three things block a credible completion claim, in order. First, the specification: 65 code-derived requirements are a provisional baseline, and a requirement nobody implemented leaves no code trace to find. Second, integration evidence: 240 passing unit tests cover domain logic thoroughly and cover the four production integrations not at all. Third, device evidence: the two Apple Intelligence features and the camera cannot run on a simulator, so the app's headline capability has not been observed working by this audit.
